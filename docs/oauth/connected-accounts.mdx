---
title: "Connected accounts"
description: "Listing a user's identities, removing one, and the edges that follow: the refusal to delete an account's last way in, the sessions an unlink revokes, and an account provisioned with no password at all."
---

`ListIdentities` and `UnlinkIdentity` are what a "connected accounts" screen is
built from. Both are scoped to one user, and both have an edge worth
understanding before you render a "Disconnect" button.

{/* verify:import */}
```go
import (
	"context"
	"errors"
	"fmt"
	"time"

	"github.com/bernardoforcillo/authlayer/auth"
	"github.com/bernardoforcillo/authlayer/store/memory"
)
```

{/* verify:main */}
```go
key := []byte("32-bytes-or-more-from-your-vault")
svc := auth.New(memory.NewAuthStore(),
	auth.WithIdentityStore(memory.NewIdentityStore()),
	auth.WithJWT([][]byte{key}, 15*time.Minute))
ctx := context.Background()

// Ida arrives from Google and is provisioned: one identity, no password.
res, err := svc.SignInWith(ctx, auth.SignInRequest{
	Identity: auth.ExternalIdentity{
		Provider: "google", Subject: "5005",
		Email: "ida@example.com", EmailVerified: true,
	},
})
fmt.Println(err, res.Created)
```

```
<nil> true
```

## The last credential

{/* verify:main */}
```go
err = svc.UnlinkIdentity(ctx, res.User.ID, "google")
fmt.Println(errors.Is(err, auth.ErrLastCredential))

rows, _ := svc.ListIdentities(ctx, res.User.ID)
fmt.Println(len(rows)) // the row survives — nothing was deleted
```

```
true
1
```

<Warning>
Removing that identity would leave an account **nothing in this package can
authenticate**: `Login` refuses an empty `PasswordHash`, and `SignInWith` would
have no link to resolve. The lockout would be permanent and silent, so the
removal is refused and **nothing** is deleted.
</Warning>

The question asked of the account is "can it **authenticate**", not "is a hash
stored". Under `WithRequireVerifiedEmail(true)` an unverified account is
refused by `Login` outright, so a password hash on one opens nothing — and
unlinking its last identity would remove the only door that does open. The
predicate reads the same option `Login` reads, so the two cannot disagree about
what a working credential is. It errs strict: an account that would in fact
have been fine is refused the unlink until it verifies its address, and the
refusal removes nothing.

`UnlinkIdentity` removes **every** row for `(userID, provider)` — nothing in the
data model forbids two identities at one provider, and "unlink this provider"
means all of them. The reachability test is on what would **remain**, not on the
user's total row count: a password-less user whose only two identities are both
at provider `P` is refused, even though the table holds two rows for them.

"There was nothing to unlink here" is a different answer, and a connected-accounts
screen acts on it differently:

{/* verify:main */}
```go
err = svc.UnlinkIdentity(ctx, res.User.ID, "github") // never linked
fmt.Println(errors.Is(err, auth.ErrIdentityNotFound))

// An unknown user id lists empty rather than erroring, so this is not an
// account-existence oracle.
none, err := svc.ListIdentities(ctx, "no-such-user")
fmt.Println(err, len(none))
```

```
true
<nil> 0
```

<Note>
A store failure **is** an error and is returned as-is. An empty list is a
statement your application acts on, so an outage must not be able to produce
one. Whether "none" arrives as an empty or a nil slice is deliberately
unspecified — `store/memory` returns an empty non-nil slice and `store/drops`
returns nil — so use `len`, never a nil comparison. Order is unspecified too;
sort if you depend on one.
</Note>

## A successful unlink signs the user out everywhere

Removing an identity is a credential removal, and every credential change in
this package sweeps session families. A successful `UnlinkIdentity` revokes
**every** family the account holds — the same "spare nothing" sweep `LogoutAll`
and `ResetPassword` perform.

<Warning>
Without it, a session minted **through the identity being removed** keeps
rotating for its full refresh TTL. "Disconnect this account" would leave the
disconnected account's session live, which is the opposite of what the button
says.
</Warning>

It sweeps all of the user's families rather than only those minted through this
identity, because a `Session` records no identity provenance — nothing in the
row says which credential minted it, and a rotated successor would not carry it
anyway. The blunt sweep is also the safer default for the case that motivates
an unlink at all: *"that Google account is not mine any more."*

There is **no carve-out for the caller's own session**, unlike
`ChangePassword`. That method is handed a `currentSessionID` it can identify
the caller's family with; this one takes no session, and a parameter for it
would ask you to nominate a session to spare with nothing here able to check
the nomination. **Say so on the screen before you call it.**

Both refusals stay total: the delete runs first, so `ErrLastCredential` and
`ErrIdentityNotFound` each reach you having changed nothing at all. A
revocation that outlived its own refused operation would sign a user out of
every device to tell them "no".

## Why the decision lives in the store

The check ("does another way in survive?") and the delete are **one atomic step**
inside `IdentityStore.DeleteIdentityIfNotLast` — not a read-then-write in the
service.

<Warning>
A user with exactly two identities and no password unlinks both at once — two
clicks, two tabs, a retried request. A "list the identities, decide, then
delete" service method has each call read the list, see a sibling, conclude the
account stays reachable, and delete. **Both deletes succeed**, the account has no
identity and no password, and nothing can sign that user in again. Both requests
returned success.

This project has shipped that exact read-then-write shape four times elsewhere
and closed it four times; this method is shaped to make it unreachable rather
than to be gotten right by whoever calls it.
</Warning>

The two shipped backends satisfy it differently, and both are covered by the
port's "one statement, one transaction, or one acquisition of the mutex":

<Columns cols={2}>
  <Card title="store/memory" icon="microchip">
    One `sync.Mutex` acquisition spans the scan, the decision and the delete —
    the same discipline every other method in that package uses.
  </Card>
  <Card title="store/drops" icon="database">
    A transaction: a per-user advisory lock, then
    `SELECT … FOR UPDATE` over the user's rows, then the `DELETE`.
  </Card>
</Columns>

A single conditional `DELETE` **cannot** do it, and the statement that looks
right is worth naming so nobody re-derives it: a statement is atomic with
respect to the rows it *writes*, but this decision is about the **other** rows —
the siblings an `EXISTS` subquery reads — and under `READ COMMITTED` that
subquery neither locks what it reads nor sees a concurrent uncommitted delete.
Both callers see the sibling, both delete. Adding `FOR UPDATE` to the subquery
trades that silent lockout for a lock-order inversion and a deadlock at the
moment a user removes a credential, which is not a fix.

## Why the store is told about the password

`DeleteIdentityIfNotLast` takes a `userHasPassword bool`. It reads like a
layering mistake — the store deciding a question it has to be *told* the answer
to — and it is not: an `IdentityStore` owns `identities` and nothing else.
`users` belongs to `auth.Store`, which may be a different backend entirely, and
giving the identity backend the ability to read a password hash would mean
handing it the credential table.

The service reads the account **fresh** on every call and passes the answer
down. What makes that safe rather than merely necessary is the direction the
value can go stale in:

| Transition | Consequence |
|---|---|
| `false` → `true` (the account gains a working password mid-call) | Refuses a delete that would in fact have been safe. Fail-closed, self-correcting on retry. |
| `true` → `false` (the account **loses** its working password mid-call) | Would allow the delete that locks it out. |

For the hash itself the dangerous direction is unreachable through `Service`:
both password writers (`ChangePassword`, `ResetPassword`) store a freshly
hashed, non-empty value, and this package offers no "remove my password" and no
account deletion at all.

<Note>
Under `WithRequireVerifiedEmail(true)` the **verified** half can move the other
way, and this page says so rather than pretending otherwise.
`Store.UpdateUserEmail` clears `EmailVerifiedAt`, and `VerifyEmail`'s
email-change path calls it before re-stamping the new address. An unlink whose
read lands in that instant passes a `true` that is false by the time the delete
runs, leaving an account with a password its configuration will not accept and
no identity.

That is **not** the permanent lockout the password case would be: the account
still holds an address it has just proved control of, so
`RequestPasswordReset` → `ResetPassword` certifies it again and restores the
login.
</Note>

<Warning>
**The one way to reach the dangerous transition** is for an application to call
`Store.UpdateUserPassword` with an empty hash itself, going around `Service`.
Such an application has removed a credential this package has no idea about; it
must not concurrently unlink identities, and if it grows a "remove my password"
feature, that feature owes the same last-credential check this method makes.
</Warning>

## An account provisioned here has no password

Not a scrubbed one — an empty column, which is a supported state. Every
`Service` method clears `PasswordHash` on the record it hands back, so the
difference is invisible from the outside; what is visible is that no password
works, including the empty string:

{/* verify:main */}
```go
_, err = svc.Login(ctx, "ida@example.com", "", "203.0.113.9", "web")
fmt.Println(errors.Is(err, auth.ErrInvalidCredentials))
```

```
true
```

`ChangePassword` cannot help either: it requires the **current** password, and
there is none to present. The only route to a first password is
`RequestPasswordReset` → `ResetPassword`, which needs no current password and
whose redemption is itself proof of control of the address the link was
delivered to:

{/* verify:main */}
```go
tok, ok, err := svc.RequestPasswordReset(ctx, "ida@example.com", "203.0.113.9")
if err == nil && ok {
	err = svc.ResetPassword(ctx, tok, "First-Password-Ever-4!")
}
login, loginErr := svc.Login(ctx, "ida@example.com", "First-Password-Ever-4!", "203.0.113.9", "web")
fmt.Println(err, loginErr, login.User.ID == res.User.ID)
```

```
<nil> <nil> true
```

`TestOAuthProvisionedUserGetsAPasswordThroughTheResetFlow` pins that arc end to
end, because a regression there would strand every externally-provisioned
account on its provider forever, with no way in if that provider is lost.

## A password reset disconnects every linked account

That same reset also removed Ida's Google link:

{/* verify:main */}
```go
rows, _ = svc.ListIdentities(ctx, res.User.ID)
fmt.Println(len(rows))
```

```
0
```

<Warning>
`ResetPassword` is **unauthenticated recovery**: whoever redeemed the token
proved control of an address and *nothing else* — no password, no session, no
device. It is therefore the one path that must assume every other credential on
the account is hostile, exactly as it already assumes every session is.

An external identity is such a credential, and the only one nothing else here
can reach. Without the sweep the documented recovery did not recover: an
attacker who had provisioned an account holding the victim's address kept
signing in through their identity after the victim reset the password, logged
in and called `LogoutAll` — every step the docs prescribe, with the account
still not theirs at the end.
</Warning>

`ChangePassword` deliberately does **not** sweep: its caller was already
authenticated and is doing something routine. Disconnecting somebody's Google
because they rotated their password is UX-hostile and buys nothing. It is the
same split this package draws between `Logout` and `LogoutAll`.

**Tell your users.** After a password reset, connected accounts must be linked
again — either by pressing "Sign in with Google" once more (rung 2 re-applies
the [linking policy](/oauth/linking), and a reset has just certified the
address, so a verified assertion links straight back) or by calling
`LinkIdentity` explicitly once they are authenticated:

{/* verify:main */}
```go
google := auth.ExternalIdentity{
	Provider: "google", Subject: "5005",
	Email: "ida@example.com", EmailVerified: true,
}
_, relinkErr := svc.LinkIdentity(ctx, res.User.ID, google)

// And now the unlink refused at the top goes through — taking her sessions
// with it, because removing a credential revokes them all.
before, _ := svc.ListSessions(ctx, res.User.ID)
unlinkErr := svc.UnlinkIdentity(ctx, res.User.ID, "google")
after, _ := svc.ListSessions(ctx, res.User.ID)
fmt.Println(relinkErr, unlinkErr, len(before), len(after))
```

```
<nil> <nil> 1 0
```

<Note>
The sweep removes links that **exist**. It cannot stop a provider that will
keep asserting the address as verified from being linked again under
`LinkVerified` — that is the trust your configuration places in that provider.
Against such a provider no local action recovers anything; the remedy is
`LinkNever`, or not configuring it.
</Note>

<Note>
A dedicated "set your first password" method would be better API than routing
people through a reset. It is **additive** and can land later without cost, and
it is deliberately not in this release. See
[the password lifecycle](/authentication/passwords) for the flow as it stands.
</Note>
