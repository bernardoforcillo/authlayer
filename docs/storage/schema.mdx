---
title: "The schema"
description: "Sixteen tables across six independent stores, printed from the code that defines them — and which constraint or index is load-bearing rather than decorative."
---

Six stores own sixteen tables between them, and none of them declares a foreign
key to another store's table — not to a users table from the RBAC side, which
authlayer does not own, not between the three auth tables, and not from
`identities` to `users` (that one is also forced: the auth store may be an
entirely different backend). Every foreign key in the package stays inside the
store that owns both its ends: `api_keys` to `service_accounts`, and the five
OAuth tables to one another.

<Note>
The column lists below are **printed by a program the documentation gate runs**,
straight out of `dropsstore.NewSchema`, `NewAuthSchema`, `NewInviteSchema`,
`NewAPIKeySchema`, `NewIdentitySchema` and `NewOAuthSchema`. They cannot drift
from the code.
</Note>

{/* verify:import */}
```go
import (
	"fmt"
	"sort"

	"github.com/bernardoforcillo/authlayer/org"
	dropsstore "github.com/bernardoforcillo/authlayer/store/drops"
	"github.com/bernardoforcillo/drops/pg"
)
```

{/* verify:decl */}
```go
func describe(t *pg.Table) {
	fmt.Println(t.Name())
	for _, c := range t.Columns() {
		flags := ""
		if c.IsPrimaryKey() {
			flags += " PK"
		}
		if c.IsUnique() {
			flags += " UNIQUE"
		}
		if !c.IsNotNull() {
			flags += " NULL"
		}
		fmt.Printf("  %s%s\n", c.Name(), flags)
	}
	if pk := t.CompositePrimaryKey(); len(pk) > 0 {
		names := make([]string, 0, len(pk))
		for _, c := range pk {
			names = append(names, c.Name())
		}
		fmt.Printf("  PRIMARY KEY %v\n", names)
	}
	var uniques []string
	for name, cols := range t.CompositeUniques() {
		names := make([]string, 0, len(cols))
		for _, c := range cols {
			names = append(names, c.Name())
		}
		uniques = append(uniques, fmt.Sprintf("  UNIQUE %v as %s", names, name))
	}
	sort.Strings(uniques)
	for _, u := range uniques {
		fmt.Println(u)
	}
	fmt.Printf("  indexes: %d\n", len(t.Indexes()))
}
```

## The RBAC tables

{/* verify:main */}
```go
s := dropsstore.NewSchema[org.Organization, org.Member]()
describe(s.Containers)
describe(s.Members)
describe(s.Roles)
```

```
organizations
  id PK
  owner_id
  created_at
  updated_at
  name
  slug UNIQUE
  indexes: 0
organization_members
  container_id
  user_id
  role_key
  joined_at
  PRIMARY KEY [container_id user_id]
  indexes: 0
organization_roles
  id PK
  container_id
  key
  name
  permissions
  created_at
  UNIQUE [container_id key] as organization_roles_container_key
  indexes: 0
```

`name` and `slug` on `organizations` are `org.Organization`'s **own** fields, not
the engine's — a [custom scope](/authorization/custom-scopes) puts yours there
instead. `permissions` is a `BYTEA` holding
[encoded grant *names*](/concepts/statements#encoding-is-by-name-not-by-bit-index),
never bit indices, which is what lets the column survive changes to your
statement set.

<Warning>
The unique constraints are load-bearing. They are what turn a concurrent
double-insert into `ErrSlugTaken`, `ErrAlreadyMember` or `ErrRoleKeyTaken`
instead of a duplicate row, **because the engine does not pre-check any of the
three**.

`CreateSchema` emits the composite ones itself — `PRIMARY KEY (container_id,
user_id)` and `UNIQUE (container_id, key)` — since drops' `CREATE TABLE` covers
single-column constraints only. Keep them if you own these tables in your own
migrations.
</Warning>

## The auth tables

{/* verify:main */}
```go
a := dropsstore.NewAuthSchema()
describe(a.Users)
describe(a.Sessions)
describe(a.Verifications)
```

```
users
  id PK
  email UNIQUE
  email_verified_at NULL
  password_hash
  created_at
  updated_at
  deleted_at NULL
  UNIQUE [email] as users_email_key
  indexes: 0
sessions
  id PK
  user_id
  token_hash
  family_id
  expires_at
  created_at
  rotated_at NULL
  user_agent
  ip
  mfa_at NULL
  UNIQUE [token_hash] as sessions_token_hash
  indexes: 1
verifications
  id PK
  user_id
  token_hash
  purpose
  email
  expires_at
  created_at
  UNIQUE [token_hash] as verifications_token_hash
  indexes: 1
```

<Note>
`email` appears **twice** — inline on the column and again as a named
constraint. That is deliberate:
`CREATE TABLE IF NOT EXISTS` is a no-op against a table that already exists, so
the guarded `ALTER TABLE` is what self-heals a users table created by an older
version or by hand.

Neither `token_hash` carries the inline flag at all, because their uniqueness is
a **MUST on the backend** rather than something declared on the record's
`drop:` tag. Both are registered as one-column constraints so `CreateSchema`
emits the `ALTER TABLE` either way.
</Note>

### All three UNIQUE constraints earn their place

<Columns cols={2}>
  <Card title="users.email" icon="user">
    What `SignUp` reads "already registered" off. Without it the duplicate
    branch never fires and
    [enumeration safety](/authentication/sign-up) has nothing to be safe about.
  </Card>
  <Card title="Both token_hash columns" icon="fingerprint">
    Keep a hash lookup single-row, and turn a generation bug into a loud error
    instead of an ambiguous multi-row match. Without the one on `sessions`,
    [`MarkRotated`'s single winner](/authentication/refresh-rotation) breaks
    with no atomicity defect at all.
  </Card>
</Columns>

### Both indexes are load-bearing too

<Columns cols={2}>
  <Card title="sessions (family_id)" icon="layer-group">
    Keeps `DeleteSessionsByFamily`'s two statements — and therefore every
    `LogoutAll` iteration — off a table scan. Every family revocation reads and
    locks by it, and `LogoutAll` runs one transaction per family.
  </Card>
  <Card title="verifications (user_id, purpose)" icon="shield-halved">
    A **security** index. It runs on every `RequestPasswordReset`, so without it
    the [residual timing channel](/authentication/rate-limiting#enumeration-safety-is-bounded-not-absolute)
    grows with the number of pending tokens held for *all* users.
  </Card>
</Columns>

Both are emitted as `CREATE INDEX IF NOT EXISTS`, so `CreateSchema` self-heals a
table missing one.

<Warning>
That second one was measured, not assumed. Seeding 40,000 other users' pending
tokens moved the known branch's floor from 2.3–2.5 ms to 4.7–5.0 ms **without**
the index, and left it at 2.4–2.8 ms **with** it. A backend that omits it — a
third-party `Store`, or your own migrations owning these tables — puts the
growth term back.
</Warning>

{/* verify:main */}

```
  role_key
  token_hash
  invited_by
  expires_at
  created_at
  UNIQUE [container_id email] as organization_invites_container_email
  UNIQUE [token_hash] as organization_invites_token_hash
  indexes: 0
organization_invite_links
  id PK
  container_id
  code
  role_key
  created_by
  max_uses
  use_count
  expires_at NULL
  revoked_at NULL
  created_at
  UNIQUE [code] as organization_invite_links_code
  indexes: 0
```

<Warning>
None of the three constraints here carries the inline `unique` flag on its
column — like the `token_hash` columns above, each is registered as a named
one-column constraint that `CreateSchema` emits as an `ALTER TABLE`. All three
are
[MUSTs on any backend](/storage/overview#the-eight-invitation-musts), and all three
bound *who gets in*:

- **`token_hash`** — what makes one emailed token pay out once.
- **`code`** — without it two concurrent redeemers resolve **different** rows
  and each atomically wins the one it picked, so a `MaxUses` limit bounds
  nothing while every individual consume behaves perfectly.
- **`(container_id, email)`** — what makes re-inviting an address replace rather
  than duplicate when two calls race. A constraint on the **pair**: the same
  person invited to two containers is two legitimate rows.
</Warning>

The comparison is byte-exact, and that is correct because the column holds only
normalized values: `CreateEmailInvite` and `DeleteEmailInvitesFor` both apply
`invite.NormalizeEmail` (trim, lowercase) first, so the constraint is on a
person rather than on a spelling and the index stays usable — no `lower(email)`
needed. See [addresses are normalized](/invitations/email-invites#addresses-are-normalized).
Rows written by **v0.1.0**, which normalized nothing, may hold non-normalized
addresses; the changelog carries the one-time migration.

## The service-account tables

{/* verify:main */}
```go
ak := dropsstore.NewAPIKeySchema()
describe(ak.ServiceAccounts)
describe(ak.Keys)
fk := ak.Keys.Col("service_account_id").ForeignKey()
fmt.Println("api_keys.service_account_id ->", fk.Target.Table().Name(), "ON DELETE", fk.OnDelete)
```

```
service_accounts
  id PK
  container_id
  name
  description
  created_by
  created_at
  updated_at
  disabled_at NULL
  indexes: 1
api_keys
  id PK
  service_account_id
  container_id
  name
  prefix
  token_hash UNIQUE
  permissions
  expires_at NULL
  last_used_at NULL
  created_by
  created_at
  revoked_at NULL
  indexes: 2
api_keys.service_account_id -> service_accounts ON DELETE CASCADE
```

<Warning>
**`token_hash` UNIQUE** is the same MUST `sessions.token_hash` carries: two rows
sharing a hash would make a presented key resolve to whichever the server
reached first, so *which account, at which cap* a bearer credential acts as
would be decided by row order. It is declared **inline**, through the record's
own `drop:"token_hash,unique"` tag, so unlike the guarded `ALTER TABLE`
constraints above `CreateSchema` cannot self-heal a pre-existing `api_keys`
table that lacks it.

**The foreign key is the cascade.** `ON DELETE CASCADE` makes a delete on the
account remove its keys in the same statement, and the constraint is what turns
a key naming no account into a foreign-key violation, classified as
`apikey.ErrServiceAccountNotFound`. `DeleteServiceAccount` still deletes the keys
explicitly inside one transaction, so the port's cascade MUST holds against a
hand-migrated schema that dropped the constraint.

**`permissions` is NOT NULL**, and empty means *no cap*: a nil
`Key.Permissions` is written as an empty `bytea`, never NULL — declare it the
same way in your own migration.
</Warning>

The three indexes serve `ListServiceAccounts` (`container_id`), `ListKeys` and
the explicit cascade (`service_account_id`), and tenant-scoped queries over
keys (`container_id`). All are `CREATE INDEX IF NOT EXISTS`.

## The identity table

{/* verify:main */}
```go
id := dropsstore.NewIdentitySchema()
describe(id.Identities)
```

```
identities
  id PK
  user_id
  provider
  subject
  email
  created_at
  last_used_at NULL
  UNIQUE [provider subject] as identities_provider_subject
  indexes: 1
```

`last_used_at` is the only nullable column here, and `nil` is a fact an
application acts on: the link exists but has
[never signed anyone in](/oauth/overview). There is **no token column**, and
that is the point — this table is the physical form of the boundary
[External identities](/oauth/overview) opens with.

### Both of these are load-bearing

<Columns cols={2}>
  <Card title="UNIQUE (provider, subject)" icon="fingerprint">
    What makes `auth.ErrIdentityLinked` a guarantee rather than advice. Without
    it two rows can name one external account against two **different** users,
    and the [sign-in ladder's](/oauth/sign-in) first rung becomes a coin flip
    over row order. It is also what fails the loser of two concurrent first
    sign-ins for the same new external account.
  </Card>
  <Card title="INDEX (user_id)" icon="layer-group">
    `ListIdentitiesByUser` — every connected-accounts screen — and the locking
    `SELECT` inside every unlink both filter on `user_id` alone. Without it both
    scan a table that grows with the whole deployment rather than with one user,
    and the unlink pays that **while holding a transaction open**.
  </Card>
</Columns>

<Note>
The constraint is composite, so `CREATE TABLE` cannot carry it at all: it is
registered through `AddUnique` and emitted as a guarded `ALTER TABLE`, the same
idiom the invitation schema uses for its own composite constraint.

That the planner actually **picks** the index is proven live rather than
assumed. `TestIdentityStoreListIdentitiesByUserUsesTheIndexLive` asserts an
index scan, with a control that drops the index and requires the plan to
degrade — an index the planner ignores is not an index.
</Note>

<Warning>
**The four UNIQUEs are load-bearing** — `code_hash`, `device_code_hash`,
`user_code`, `token_hash`. Each discharges the MUST `sessions.token_hash`
carries: the three compare-and-sets (`RedeemCode`, `SetDeviceStatus`,
`MarkRefreshRotated`) are single-winner only if a hash identifies at most one
row. All four are declared **inline** through the records' own `,unique` tag
options, so `CreateSchema` cannot self-heal them onto a pre-existing table.

**Every reference is a cascading foreign key**, because every table is owned
by this one store. They are what make `CreateGrant`, `CreateCode`,
`CreateDeviceAuthorization` and `CreateRefreshToken` refuse a row naming no
client or no grant (a foreign-key violation, classified as `ErrClientNotFound`
or `ErrGrantNotFound`), and they back the two atomic cascades —
`DeleteClient` and `RevokeGrant` delete their dependents explicitly inside one
transaction, with the constraints as the backstop.
`oauth_device_authorizations.grant_id` deliberately has **no** foreign key: it
is `NULL` until approval and its row is inert once the grant is gone.

**`redirect_uris`, `grant_types` and `scopes` are `jsonb`** — one array each.
They are application-shaped lists no query filters on, so a child table per
list would be three joins on every client load, and a `text[]` is a driver
type `database/sql` cannot scan into a Go slice. A nil list is written as
`[]`, never `NULL`. `container_id`, `service_account_id` and `created_by` are
nullable because an application-level or dynamically registered client has
none of them and `""` is not a `uuid`; `ListClients("")` queries
`container_id IS NULL`.
</Warning>

The nine indexes serve `ListClients` (`container_id`), `ListGrantsByUser`
(`user_id`), `DeleteRefreshFamily` (`family_id`), and the client and grant
cascades (`client_id`, `grant_id` on each dependent table). The four UNIQUE
columns are the lookup keys every token path uses and need no separate index.

## Column types

Every id column is a PostgreSQL `uuid` **by default** — including the ones
holding a user id, since authlayer mints those too. See
[Ids](/concepts/ids) for the options that retype them, and for the deployment
failure that only shows up against a real database.

Timestamps are `timestamptz`-shaped. The columns marked `NULL` above are the
only ones that may hold it: the nullable stamps (`email_verified_at`,
`deleted_at`, `rotated_at`, a link's `expires_at` and `revoked_at`, and their
OAuth counterparts), and the three ids an application-level OAuth client
leaves empty.

`users.deleted_at` is the anonymization stamp — `NULL` on every ordinary
account. It arrives on a **fresh** table only: `CreateSchema` self-heals a
missing constraint or index, but a column lives inside the
`CREATE TABLE IF NOT EXISTS` that no-ops against a table that already exists.
A users table created by **v0.1.0** needs one hand-run migration before this
store can write to it at all, since every `INSERT` names the column:

```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS deleted_at timestamptz;
```

## Owning these tables yourself

`st.Schema()`, `NewAuthSchema()` and `NewInviteSchema()` expose the definitions
if you would rather generate DDL for your own migration tool. If you do, keep
every constraint and index on this page — each one is here because something
breaks without it, and the two indexes are the ones most easily dropped by
accident.
