The stores are written to a small set of rules, so a new table, index or store
looks like the ones beside it. Each rule below names the test that fails when it
is broken; none of them is only prose.

## One option type

Every store and schema constructor in `store/drops` takes the same
`dropsstore.Option`. A constructor reads the settings that concern it and ignores
the rest, so one list configures a deployment:

{/* verify:skip a one-line fragment: it needs no database, and the options it names are exercised by store/drops options_test.go */}
```go
opts := []dropsstore.Option{dropsstore.TextLibraryIDs()}
```

`WithAuthNames`, `WithOAuthNames` and the other `With*Names` options set one
store's table names. `TextLibraryIDs()` and `TextUserIDs()` retype id columns
from `uuid` to `text`; on the stores that own the users table (auth, identity,
credential, MFA) the user ids are minted by the library, so `TextLibraryIDs`
also retypes `user_id` and `TextUserIDs` is ignored. The per-store type names
(`AuthOption`, `InviteOption`, ...) are aliases of `Option`.

## Tables, constraints and indexes

- **Default table names are unique** across all stores, so one database holds
  every store without renaming (`TestContractDefaultTableNamesAreUnique`).
- **An index is named for what it covers:** `<table>_<columns>_idx`
  (`TestContractIndexNamesSayWhatTheyCover`). The audit event and consent
  indexes predate the rule and keep their names, because renaming would leave a
  duplicate of each on every deployed database.
- **A column a janitor deletes by leads an index.** That is `expires_at` on every
  table, and `revoked_at` on `api_keys` and `oauth_grants`, whose purge also
  deletes by it (`TestContractPurgedColumnsAreIndexed`).
- **Constraints that decide correctness are load-bearing.** A unique violation
  is what turns a concurrent double-insert into a typed error, because the
  engine does not pre-check, so they are emitted by `CreateSchema` and by the
  migrations, never left to the in-memory registry.

## The tables are a formal model

`dropsstore.Tables()` returns every table as a `*pg.Table`, in creation order,
and `dropsstore.SnapshotSchema()` returns drops' snapshot of them: each column
with its SQL type and nullability, the keys, foreign keys and indexes, as a
value that marshals to the same bytes every time. All 25 tables are in it,
audit and consent included (`raw_tables.go`): their partial indexes and defaults
are declared on the table, and only the audit guard functions and triggers stay
SQL text. The scope tables carry the engine's base columns.

The model is frozen in `store/drops/testdata/schema.snapshot.json`.
`TestSnapshotMatchesGolden` fails on any change to a table, column, type, key or
index, so a schema change always appears as a diff in review. After an intended
change, regenerate it with `UPDATE_GOLDEN=1 go test ./store/drops -run
TestSnapshotMatchesGolden` and add a migration step. Diffing two releases'
snapshots with drops' tooling shows what that step has to do.

The column rules over those tables, each a test in `catalog_test.go`:

| Rule | Test |
|---|---|
| Table and column names are lower snake_case | `TestContractNamesAreSnakeCase` |
| Every table has a primary key; a single-column one is `id` (`mfa_factors`, one row per user, is keyed by `user_id`) | `TestContractEveryTableHasAKeyAndEntityKeysAreCalledID` |
| `*_at` is `timestamptz`; `created_at` is `NOT NULL`; `permissions` is `NOT NULL bytea`; booleans are `NOT NULL`; `id` is `uuid` or `text` | `TestContractColumnTypes` |
| A hash a bearer secret is resolved by is `UNIQUE`; only `password_hash`, `oauth_clients.secret_hash` and `mfa_recovery_codes.code_hash` are exempt | `TestContractLookupHashesAreUnique` |
| A foreign key never crosses stores, and its column leads an index | `TestContractForeignKeys` |
| A composite foreign key stays in its store, leads an index, and targets a `UNIQUE` or primary key; a repeated column is guarded or listed with a reason | `TestContractCompositeForeignKeys`, `TestContractRepeatedColumnsAreGuarded` |
| `Tables()` lists exactly the tables the stores own | `TestTablesCoverEveryStoreTable` |

## Normalization

The tables are in first normal form except where a column holds a set the engine
always reads whole (`permissions` as encoded grant names, `oauth_clients`'
`redirect_uris`, `grant_types` and `scopes` as JSON arrays, the space-separated
OAuth `scope`). They are in second normal form: the two composite-keyed tables,
`organization_members` and `organization_roles`, have only attributes that depend
on their whole key.

Third normal form is where a column can repeat what a parent row already
determines. Three do, and each is now guarded by a composite foreign key, so the
database refuses a row that disagrees with its parent instead of trusting the
code that wrote it:

| Child column pair | Parent | Guards against |
|---|---|---|
| `api_keys (service_account_id, container_id)` | `service_accounts (id, container_id)` | a key in a different container than its account |
| `oauth_codes (grant_id, client_id)` | `oauth_grants (id, client_id)` | a code for a different client than its grant |
| `oauth_refresh_tokens (grant_id, client_id)` | `oauth_grants (id, client_id)` | a refresh token for a different client than its grant |

The copies stay, rather than being dropped in favour of a join, because the
lookup that matters (`FindKeyByHash`, redeeming a code) reads them on the hot
path and the ports expose them. A composite foreign key needs a `UNIQUE` on the
parent's referenced pair, which is why `service_accounts (id, container_id)` and
`oauth_grants (id, client_id)` are unique.

Four repeats are deliberately not guarded, and `TestContractRepeatedColumnsAreGuarded`
lists each with its reason: `oauth_device_authorizations.client_id` (its
`grant_id` is null until the user approves), `oauth_clients.container_id` (its
service account belongs to another store), `sessions.user_id` and
`oauth_refresh_tokens.family_id` (a family has no table of its own).

The keys are added `NOT VALID`: PostgreSQL enforces them on every new write at
once, without scanning the table or failing on old rows. `CreateSchema` then
validates them if the data allows and otherwise leaves them `NOT VALID` without
error, so a deployment's startup never depends on old data. The `-003_relations`
migration validates strictly and fails, naming the constraint, when existing
rows already disagree; fix them and run it again.

## Schema creation has one path

`CreateSchema` and the migrations both build from the same table definitions, via
one routine: `CREATE TABLE IF NOT EXISTS`, the composite constraints a `CREATE
TABLE` cannot carry, then `CREATE INDEX IF NOT EXISTS` for each registered
index. Every statement is idempotent and additive.

## Migrations are a chain per store

Each store's `Migrations()` returns nodes on the `authlayer` branch of drops'
`TreeMigrator` (see [PostgreSQL](/storage/postgres)):

- `-001_tables` is the root: no parent, no `Down`, because dropping a table is
  data loss.
- `-002_indexes` depends on it and is reversible. It carries every index added
  after the 0.3.1 baseline, registered through `addIndex`.
- `-003_relations` depends on the step before it and is reversible. It adds the
  `UNIQUE` targets (registered through `addUnique`) and the composite foreign
  keys, then validates each strictly.
- A later release adds a new node whose parent is the previous one; it never
  edits a node that has shipped.
- IDs embed the store's first table name, so two instances of one generic store
  under `WithNames` do not collide.

`TestContractMigrationsAreAFormalChain` and `TestContractLateIndexesAreRegistered`
enforce the shape, and an integration test runs the chain against PostgreSQL:
fresh database, rollback and re-apply of the index step, and adopting a database
`CreateSchema` already built.

## Writing a store method

The statements that carry meaning are written out: conditional `UPDATE`s,
locking `SELECT`s and multi-step transactions. The plain ones go through four
generic helpers that take a `*pg.DB`, so they work on a store's connection and
inside `InTx` alike:

| Helper | Does |
|---|---|
| `findOne[T]` | one row by predicate, or the store's not-found error |
| `listWhere[T]` | every matching row; none is a nil slice, not an error |
| `updateOne` | update by predicate, not-found error when no row matched |
| `deleteOne` | delete by predicate, not-found error when no row matched |

Housekeeping deletes go through `deleteBatched`, which removes rows in batches
of 5000 per statement instead of one unbounded `DELETE`.

## The in-memory store has the same shape

`store/memory` keeps one `table[V]` per collection (`get`, `insert`, `update`,
`remove`, `filter`). The table has no lock of its own: each store method holds
the store's single mutex for its whole body, which is what keeps a
check-then-write across two tables atomic.

## Shared option helpers

Every service's `WithClock`, `WithIDGenerator`, `WithRuntime` and `WithHooks` is
built from `core.Override`, `core.Runtime.Apply` and `core.AppendNonNil`, so
"a nil value is ignored" is written once.
