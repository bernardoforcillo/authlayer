---
title: "The password lifecycle"
description: "Change, reset, the strength policy, and the two sweeps that close two real side doors — sequentially only, which is stated rather than papered over."
---

Three calls move a password credential, and each one revokes sessions
differently.

| Call | Requires | Revokes |
|---|---|---|
| `ChangePassword(ctx, userID, currentSessionID, current, next)` | the **current password** | every session **except** the caller's own family |
| `RequestPasswordReset(ctx, email, ip)` | nothing — and never errors on an unknown address | nothing |
| `ResetPassword(ctx, plainToken, next)` | a valid, unexpired `password_reset` token | **every** session the account has |

<Note>
Everything on this page is demonstrated in order by `go run ./examples/reset`,
which runs against `store/memory` and needs no database.
</Note>

## The strength policy

`password.DefaultRules()`: **12 characters**, an upper, a lower, a digit, and
one character that is neither a letter, a digit, **nor whitespace** — so padding
a short password with spaces cannot satisfy it.

{/* verify:import */}
```go
import (
	"context"
	"errors"
	"fmt"
	"time"

	"github.com/bernardoforcillo/authlayer/auth"
	"github.com/bernardoforcillo/authlayer/password"
	"github.com/bernardoforcillo/authlayer/store/memory"
)
```

{/* verify:main */}
```go
rules := password.DefaultRules()
fmt.Println(rules.MinLength, rules.RequireUpper, rules.RequireLower,
	rules.RequireDigit, rules.RequireSpecial)

fmt.Println(password.Validate("short", rules))
fmt.Println(password.Validate("aaaaaaaaaaaa    ", rules))
fmt.Println(password.Validate("Correct-Horse-Battery-7", rules))
```

```
12 true true true true
[min_length upper digit special]
[upper digit special]
[]
```

`Validate` returns the **names** of the failed rules, so a handler can render a
stable message. Swap the policy with `auth.WithRules(r)`, and the algorithm with
`auth.WithHasher(h)` — `password.Hasher` is a three-method port with a bcrypt
default.

<Warning>
`Hasher.Dummy` exists solely to spend comparable bcrypt time on a
user-not-found path. Deleting it because "the result is discarded" silently
reinstates a timing oracle — discarding the result is the point.
</Warning>

`password` defines **no sentinels**: `Validate` returns rule names and `Verify`
returns a bool, so there is nothing to compare with `errors.Is`. The service
wraps a failure as `auth.ErrWeakPassword`, which wraps the failed rule names.

## `ChangePassword` spares the caller's own family

Pass the `sid` from the access token that authenticated the request — which is
what [`VerifyAccessToken`](/authentication/access-tokens) hands you.

{/* verify:main */}
```go
key := []byte("32-bytes-or-more-from-your-vault")
svc := auth.New(memory.NewAuthStore(), auth.WithJWT([][]byte{key}, 15*time.Minute))

ctx := context.Background()
res, _ := svc.SignUp(ctx, "bob@example.com", "Correct-Horse-Battery-7")
_, _ = svc.VerifyEmail(ctx, res.VerifyToken)

laptop, _ := svc.Login(ctx, "bob@example.com", "Correct-Horse-Battery-7", "203.0.113.9", "laptop")
_, _ = svc.Login(ctx, "bob@example.com", "Correct-Horse-Battery-7", "198.51.100.7", "phone")

claims, _ := svc.VerifyAccessToken(laptop.AccessToken)
err := svc.ChangePassword(ctx, res.User.ID, claims.SessionID,
	"Correct-Horse-Battery-7", "Another-Valid-Pass22!")
fmt.Println("change:", err)

_, err = svc.Refresh(ctx, laptop.RefreshToken)
fmt.Println("the caller's own family survives:", err)

rows, _ := svc.ListSessions(ctx, res.User.ID)
fmt.Println("the phone is gone:", len(rows))
```

```
change: <nil>
the caller's own family survives: <nil>
the phone is gone: 2
```

Two rows remain because the laptop just rotated: one live successor and one
retained tripwire, both in the caller's own family. The phone's family is gone.

<Warning>
An **empty or foreign** `currentSessionID` revokes everything, which is the
fail-closed direction. Do not pass `""` because it is convenient.
</Warning>

A wrong current password is `ErrInvalidCredentials`, and an account with **no**
password credential spends a comparable `Dummy` and gets the same error.

## `RequestPasswordReset` never errors on an unknown address

{/* verify:main */}
```go
known, ok, err := svc.RequestPasswordReset(ctx, "bob@example.com", "203.0.113.9")
fmt.Println("known:  ", known != "", ok, err)

unknown, ok, err := svc.RequestPasswordReset(ctx, "nobody@example.com", "203.0.113.9")
fmt.Println("unknown:", unknown != "", ok, err)

_, _, err = svc.RequestPasswordReset(ctx, "bob@example.com", "")
fmt.Println("empty ip:", errors.Is(err, auth.ErrMissingIP))
```

```
known:   true true <nil>
unknown: false false <nil>
empty ip: true
```

Both return the same `(token, ok, nil)` shape, so a handler has nothing to
branch on but `ok` — and `ok` decides **whether to send mail**, never what to
tell the client. The same fixed-response obligation as
[sign-up](/authentication/sign-up#what-the-caller-must-do) applies here.

### Re-issuing kills the previous token

{/* verify:main */}
```go
second, _, _ := svc.RequestPasswordReset(ctx, "bob@example.com", "203.0.113.9")
fmt.Println("the first token is dead:",
	errors.Is(svc.ResetPassword(ctx, known, "Reset-Horse-Battery-1!"),
		auth.ErrVerificationNotFound))
```

```
the first token is dead: true
```

<Warning>
That falls out of the re-issue contract itself, and it is a nuisance lever:
anyone who merely knows an address — no credential, no relationship to the
account — can kill a victim's genuine pending reset link by looping calls.
`WithPasswordResetRateLimiter` is what bounds how often that can happen. There
is **no default**; the bucket size is an operator decision.
</Warning>

## `ResetPassword` claims first, applies second

A failure after the claim burns the token rather than leaving it redeemable
twice. It then revokes **every** session the account has — no "spare the
caller's own" exception, because presenting a reset token is no evidence the
caller is using any of the account's existing sessions.

{/* verify:main */}
```go
fmt.Println("reset:", svc.ResetPassword(ctx, second, "Reset-Horse-Battery-1!"))
fmt.Println("the same token twice:",
	errors.Is(svc.ResetPassword(ctx, second, "Another-One-2!"),
		auth.ErrVerificationNotFound))

rows, _ = svc.ListSessions(ctx, res.User.ID)
fmt.Println("sessions after a reset:", len(rows))

_, err = svc.Login(ctx, "bob@example.com", "Another-Valid-Pass22!", "203.0.113.9", "laptop")
fmt.Println("the old password is dead:", errors.Is(err, auth.ErrInvalidCredentials))
_, err = svc.Login(ctx, "bob@example.com", "Reset-Horse-Battery-1!", "203.0.113.9", "laptop")
fmt.Println("the new one works:", err)
```

```
reset: <nil>
the same token twice: true
sessions after a reset: 0
the old password is dead: true
the new one works: <nil>
```

## A completed reset also verifies the address

A reset token is only ever deliverable to the address it was minted for, so
redeeming one **is** proof of control of that address — the same proof a signup
token carries, arriving through a different door.

{/* verify:main */}
```go
never, _ := svc.SignUp(ctx, "carol@example.com", "Correct-Horse-Battery-7")
before, _ := svc.User(ctx, never.User.ID)
fmt.Println("carol never confirmed:", before.EmailVerifiedAt == nil)

tok, _, _ := svc.RequestPasswordReset(ctx, "carol@example.com", "198.51.100.7")
_ = svc.ResetPassword(ctx, tok, "Reset-Horse-Battery-2!")

after, _ := svc.User(ctx, never.User.ID)
fmt.Println("a completed reset stamped it:", after.EmailVerifiedAt != nil)

// A second reset leaves the ORIGINAL stamp alone.
stamp := *after.EmailVerifiedAt
tok2, _, _ := svc.RequestPasswordReset(ctx, "carol@example.com", "198.51.100.7")
_ = svc.ResetPassword(ctx, tok2, "Reset-Horse-Battery-3!")
again, _ := svc.User(ctx, never.User.ID)
fmt.Println("not re-stamped:", again.EmailVerifiedAt.Equal(stamp))
```

```
carol never confirmed: true
a completed reset stamped it: true
not re-stamped: true
```

<Note>
Without that, `WithRequireVerifiedEmail(true)` had **no way out**, because
authlayer exposes no verification-resend path: someone who signed up with an
address they did not own permanently denied the real owner that address, and a
user whose signup mail was lost was locked out for good.

Two guards keep it honest. An already-verified address keeps its original
timestamp, and an account whose address **changed** since the token was minted
is not certified at all — the proof is about the address the token was
*delivered* to, and `Store.MarkEmailVerified` re-checks that atomically rather
than trusting whatever the row now holds.
</Note>

## The two sweeps

`ChangePassword`, `ResetPassword` and `LogoutAll` each invalidate every
outstanding `password_reset` **and** `email_change` token for the account. That
closes two real side doors:

<Columns cols={2}>
  <Card title="The parked reset link" icon="link-slash">
    An attacker who requested a reset and waited would otherwise keep a working
    way in for that token's whole hour — even after the victim changed their
    password, the one thing a user does on suspecting compromise.
  </Card>
  <Card title="The armed email change" icon="envelope-open-text">
    Stronger. That token lives **24 hours** by default and `VerifyEmail` redeems
    it with **no authentication at all**, moving the account to the attacker's
    address — after which the victim cannot recover, because `Login` and
    `RequestPasswordReset` both look accounts up *by email*.
  </Card>
</Columns>

`LogoutAll` is in that list because "sign out of every device" is precisely what
a user clicks on spotting an intruder; sweeping only on the two credential paths
meant the takeover survived it. `Logout` and `RevokeSession` sweep **nothing**,
deliberately — they are per-device and routine.

The mirror holds too: redeeming an `email_change` invalidates the account's
outstanding `password_reset` tokens. See
[Email verification and change](/authentication/email-verification#the-mirror-sweep).

### Both sweeps are sequential-only

<Warning>
Nothing orders either sweep against a `RequestPasswordReset` or
`RequestEmailChange` whose own `Store.CreateVerification` is **genuinely
concurrent**.

Park such a mint, run a full `ChangePassword` — the sweep finds nothing —
release the mint, and the resulting token **survives and later redeems**. That
is demonstrated deterministically in the package's own tests, not hypothesised.

Closing that window for real needs a transaction spanning both the sweep and the
mint, which the `Store` port does not offer. The sequential case is closed; the
concurrent one is not, and this is stated rather than papered over.
</Warning>

{/* verify:main */}
```go
// The sequential case, which IS closed.
victim, _ := svc.SignUp(ctx, "dana@example.com", "Correct-Horse-Battery-7")
_, _ = svc.VerifyEmail(ctx, victim.VerifyToken)
session, _ := svc.Login(ctx, "dana@example.com", "Correct-Horse-Battery-7", "203.0.113.9", "laptop")

parked, _, _ := svc.RequestPasswordReset(ctx, "dana@example.com", "198.51.100.66")
c, _ := svc.VerifyAccessToken(session.AccessToken)
_ = svc.ChangePassword(ctx, victim.User.ID, c.SessionID,
	"Correct-Horse-Battery-7", "Changed-Horse-Battery-2!")

fmt.Println("the parked token was swept:",
	errors.Is(svc.ResetPassword(ctx, parked, "Attacker-Owns-This-3!"),
		auth.ErrVerificationNotFound))
```

```
the parked token was swept: true
```
